Design notes

FPGA image scalers compared: nearest, bilinear, bicubic and Lanczos

Published 2026-10-01

The library has a family of streaming image scalers that share one framework and differ only in the filter kernel. These notes explain what they share, how each kernel works, what each costs on a 7-series FPGA, and how to pick one. All of them take and produce AXI4-Stream video (tuser = start of frame, tlast = end of line), are controlled over AXI4-Lite, and produce one output pixel per clock.

The shared framework

  • scaler_dda walks the output raster and produces, for every output pixel, the matching source coordinate in 16.16 fixed point: src = OFFS + o × STEP, accumulated exactly. The scale factor is just STEP (for example 0x0000_AAAB ≈ 2/3 for a 1.5× upscale), so any ratio works, up or down, independently in X and Y.
  • banked_framebuf stores the input and returns a whole TAPS × TAPS window of neighbouring pixels every clock. It does this by splitting the image over B × B RAM banks (B = next power of 2 ≥ TAPS), so every pixel in any window lives in a different bank. Out-of-image taps are clamped to the edge.
  • scaler_ctrl owns the common register map (0x000–0x02F), captures input frames, detects start-of-frame/end-of-line errors and sequences frames. Kernel-specific registers start at 0x040.

Each scaler is therefore "DDA + window buffer + kernel", and swapping the kernel is how you trade quality for area.

The kernels

Nearest neighbour

out = in(round(src_x), round(src_y)). One tap, no arithmetic on pixel data. It keeps hard edges perfectly sharp and adds no blur, but produces blocky, uneven pixels at non-integer ratios and aliases badly when downscaling. It's the right choice for integer upscales of pixel art, UI or text overlays, or when area matters most.

Bilinear (2×2)

A weighted average of the four surrounding pixels, with weights from the fractional part of the coordinate (8 phase bits by default). The weights are computed in hardware, so there are no tables to program. It's smooth and cheap, but softens edges, especially on upscales.

Bicubic (4×4) and Lanczos-3 (6×6): polyphase FIR

Both are thin wrappers around scaler_polyphase, a separable polyphase FIR. The fractional coordinate is rounded to PHASE_BITS (default 6, so 64 phases), which selects one row of a programmable coefficient table. Filtering runs vertically first, then horizontally:

v_k = (Σ_j CV[py][j] · in[y0+j][x0+k] + 2^(F-1)) >>> F
out = clamp((Σ_k CH[px][k] · v_k + 2^(F-1)) >>> F)        // F = COEF_FRAC = 14

Coefficients are signed 16-bit (14 fraction bits) and live in AXI4-Lite-writable tables at 0x1000 (horizontal) and 0x2000 (vertical). That makes the kernel a run-time choice, not a synthesis choice. With 4 taps you can load any Mitchell–Netravali cubic: Catmull-Rom (B=0, C=0.5) for sharpness, Mitchell (1/3, 1/3) for the usual balance, or the B-spline (1, 0) for maximum smoothness. Lanczos-3 uses sinc(x)·sinc(x/3) over 6 taps for the sharpest result. Its negative lobes can overshoot, so the output is clamped to the pixel range. The tables are generated by tools/scaler_coefs.py, normalized to unity DC gain, and should only be rewritten while the scaler is idle.

scaler_polyphase can also be used directly with up to 16 taps, for example 8–12-tap low-pass kernels for heavy downscaling without aliasing.

The DSP count is exactly the multiplier count: bicubic needs 3 colours × (16 vertical + 4 horizontal) = 60 multipliers plus 5 for address arithmetic, and Lanczos 3 × (36 + 6) = 126 plus 9. About half of Lanczos's LUTs are the 6×6 window multiplexer, since each of 36 taps selects from 64 banks. These are pre-place-and-route estimates with conservative DSP packing; Vivado typically absorbs many of the fabric pipeline registers into the DSP48s and lands noticeably lower.

Frame buffer or line buffer

Memory usually dominates. Each scaler has three buffering modes, chosen with parameters and sharing the same registers and output:

ModeStores1920×1080 RGB888Behaviour
Frame buffer (default)1 frame49.8 MbitCapture a frame, then output it; input stalls during output
PINGPONG=12 frames99.5 MbitCapture the next frame while outputting the current one
LINE_BUF=14–8 lines184–369 kbitOutput starts a few lines after input; needs STEP_Y ≥ 0

A 640×480 frame fits mid-range FPGA block RAM; a 1080p frame needs UltraRAM or external DDR. Line-buffer mode brings 1080p down to about 0.4 Mbit, which fits on essentially any FPGA, and has been simulated end to end on a real 1920×1080 frame with Lanczos-3.

How to choose

  • Integer upscales, pixel art, text overlays, smallest area: nearest.
  • General video on a budget, mild ratio changes: bilinear.
  • Best quality per LUT for video upscaling: bicubic with Catmull-Rom or Mitchell coefficients.
  • Maximum sharpness, large upscales, plenty of DSPs: Lanczos-3, or the spatial upscaler (Lanczos followed by contrast-adaptive sharpening).
  • Large downscales (more than 2×): polyphase with 8–12 low-pass taps, or the mip-map based trilinear and anisotropic scalers, which filter properly where few-tap kernels would alias.
  • Edges that must stay crisp without ringing: the edge-directed scaler.

In most designs, pick the buffering mode first (it sets memory), then the kernel (it sets DSPs and LUTs).

Verification

Each scaler has a self-checking testbench that compares every output pixel bit-exactly against an independent reference model, with AXI protocol checkers (procedural and SVA) on every interface. The suite covers identity, non-integer up and down ratios, random tvalid/tready stalls and maximum size, in all three buffering modes. The Lanczos-3 line-buffer build was also run on a real 1920×1080 image scaled to 1280×720, with all 921,600 output pixels matching. The testbenches can also scale a real image (./run.sh +IMG=photo.ppm) and write the result as a PPM for visual inspection. A gate-level flow re-runs the same testbench on the synthesized Xilinx netlist, block RAMs and DSP48s included.
