Design notes

Lens Distortion Correction: pipeline design decisions

This is a walkthrough of the design decisions behind the lens-distortion-correction demo — a streaming SystemVerilog IP that corrects barrel/pincushion lens distortion on live AXI4-Stream video, entirely with on-chip memory.

Why on-chip only, no external DDR

The frame buffer (frame_buffer.sv) is a 4x-replicated internal BRAM store. Skipping an external-DDR path keeps the demo synthesizable end-to-end in Yosys without a memory controller, and keeps the read side free of arbitration: each of the four bilinear taps gets its own port, so there's never a read-port conflict inside a single pixel request.

Why fixed-point Q16.16, not floating point

barrel_pkg.sv defines the Q16.16 format shared by the whole datapath. Radial/tangential distortion math (coord_gen.sv) and the AXI4-Lite derived-configuration path both run on qmul()/qsat() helpers built on top of a single 2-cycle pipelined multiplier (mulq_s.sv). Fixed-point keeps every multiply mappable to a small, fixed number of DSP48E1 slices with predictable latency — floating point would cost far more area for precision this design doesn't need.

Latency budget

Coordinate generation is a fixed 23-cycle pipeline that never stalls, one pixel per clock. A tag delay line re-creates tlast/tuser 31 cycles behind the request that produced them, so the output AXI4-Stream framing stays correct without the raster generator needing to know anything about interpolation latency downstream.

Verification strategy

Every sub-block (fixed_recip, mulq_s, frame_buffer, coord_gen, bilinear) has its own self-checking testbench with an independent golden reference, runnable standalone in seconds. The full image_system_demo regression then checks the assembled pipeline bit-exact against a separate golden model, using a synthetically generated test chart — there's no external image dependency, so the regression is fully reproducible from a clean clone.
