AXI-Stream width converter: upsizing, downsizing and tkeep

Published 2026-10-01

These notes cover the axi_stream_width_converter core, which changes the data width of an AXI4-Stream between IN_BYTES and OUT_BYTES. A typical use is narrowing a 32-bit DMA stream into a byte-wide UART or SPI path, or packing an 8-bit sensor stream into 32-bit words before it is written to memory. One width must be an integer multiple of the other; if they are equal, the core reduces to a register slice.

Interface and byte order

axi_stream_width_converter #(
  .IN_BYTES (4),   // s_axis_tdata is 32 bits
  .OUT_BYTES(1),   // m_axis_tdata is 8 bits
  .USER_W   (1)
) u_wc ( .aclk, .aresetn, .s_axis_*, .m_axis_*, .keep_err_o );

Byte order is little-endian, as in the AXI4-Stream convention: byte 0 of the wide word (tdata[7:0]) is the first byte on the narrow side. Ratios that aren't whole multiples (for example 3 → 2 bytes) are rejected at elaboration with $error, so the mistake shows up at build time rather than as corrupted data on hardware.

Downsizing (wide → narrow)

The downsizer captures one input beat and then sends it out in RATIO = IN_BYTES / OUT_BYTES chunks, selecting each chunk with an index into the held word. Two details make it packet-correct:

  • Trailing empty chunks are skipped. On the last beat of a packet, the core finds the highest chunk with any tkeep bit set and stops there. A 7-byte packet on a 4 → 1 converter therefore produces exactly 7 output beats, not 8 with one empty byte.
  • tlast moves to the last valid chunk. It is asserted on the final chunk the core actually sends, so downstream logic sees a clean packet boundary.

Non-last beats always send every chunk, because AXI4-Stream only allows null bytes at the end of a packet in the usual "continuous aligned" usage.

Upsizing (narrow → wide)

The upsizer writes each input beat into its slot of the wide output word, along with its tkeep bits, and asserts m_axis_tvalid once the word is full. If tlast arrives before the word fills, the core flushes early: the partial word goes out with tlast set and tkeep marking only the bytes that were filled. A new packet always starts at byte 0 of a fresh output word, so packets are never merged into the same beat.

tuser and tkeep rules

  • tuser is carried on the tlast beat only. This suits the common use of tuser as a per-packet flag, such as an error or drop marker. A per-byte sideband would need a different design.
  • tkeep must be contiguous from byte 0 (0001, 0011, 0111, 1111). The check is a single expression: (tkeep & (tkeep + 1)) == 0. A beat with a gap is passed through as given, and keep_err_o pulses for one clock so system logic can count or trap the error.

Latency and throughput

Latency is one clock for downsizing and equal widths. For upsizing it is the ratio in clocks, since the core has to collect a whole word before sending it. The control logic is deliberately minimal — one data register and a counter, with no skid buffer. The cost is a single idle cycle between words: the downsizer accepts a new input beat in the cycle after the last chunk leaves, and the upsizer accepts new input in the cycle after the full word is taken. With 4:1, that means 4 narrow beats every 5 clocks. If a link has to run at 100% on the narrow side, add an AXI-Stream FIFO or a register slice on the wide side.

Verification

The self-checking testbench sends 200 random packets (random length, partial final tkeep) through 4→1, 4→2, 1→4, 2→4 and 4→4 instances with random stalls on both handshakes. A reference model compares the byte stream, packet boundaries and tuser at byte level. A downsize-then-upsize round trip must also reproduce the original beats exactly, which catches byte-order and tkeep mistakes that a single direction could miss.
